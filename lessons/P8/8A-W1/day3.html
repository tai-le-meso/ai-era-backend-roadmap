Build the core — Architecture styles: the honest comparison

Architecture Design at Scale · Phase 8 — Solution Architecture · ~4.5h
Day 1Day 2Day 3 — Build the coreDay 4↑ Week overview
What I learn
The honest failure story per styleEach style fails characteristically. Monolith: deployment coupling and blast radius. Microservices: distributed debugging and consistency bugs. Event-driven: no single place shows the flow. Serverless: cold starts and vendor lock-in. Naming them is what makes a recommendation trustworthy.
Team topology fitConway's Law again: the architecture that fits three engineers is not the architecture that fits thirty. Stating team size as an input to the decision is what most style debates omit.
What I do
  1. Write the characteristic failure story for each style.
  2. Add team size and topology explicitly as decision inputs.
  3. Finalise the comparison with your recommendation.
  4. Commit the detectors alongside.
What I conclude
  • A recommendation that names its own failure mode is more credible than one that does not.
  • Team size belongs in every architecture-style discussion and is usually left out.
What I remember & apply
Name each style's characteristic failure → apply: it makes your recommendation credible.
Team size is a decision input → apply: state it explicitly in the comparison.
