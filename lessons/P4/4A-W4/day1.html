Learn I — Tactical DDD: entities, value objects, aggregates

Domain-Driven Design · Phase 4 — DDD & Architecture · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Entity vs value objectAn entity has identity that persists through change — the same account even after its balance changes. A value object is defined entirely by its attributes, is immutable, and has no identity — two Money objects of 100 EUR are interchangeable. You built these in 1A-W6; now they get their domain justification.
The aggregate as a consistency boundaryAn aggregate is a cluster of objects treated as one unit for data changes, with one entity as the root. Every invariant that must hold at every commit lives inside one aggregate. That is the definition — not 'objects that belong together'.
Vernon's four rules(1) Model true invariants inside the boundary. (2) Design small aggregates. (3) Reference other aggregates by identity only, never by object reference. (4) Update other aggregates eventually, via domain events. Rules 2 and 3 exist to keep transactions short and contention low — which links directly to your 2A hot-row measurements.
One aggregate per transactionIf a transaction modifies two aggregates, either the boundary is wrong or you need eventual consistency between them. This rule is what keeps aggregates from becoming a whole-database lock.
What I do
  1. Read the DDD_Aggregate article and write out the four rules.
  2. For each aggregate candidate from W3, state the invariant that defines its boundary.
  3. Find every place the current code holds an object reference to another aggregate.
  4. Predict which aggregate is too large, and what contention it causes.
What I conclude
  • The invariant defines the boundary; if you cannot name an invariant, you do not have an aggregate.
  • Large aggregates show up as lock contention — the design problem has a measurable symptom.
  • Rule 3 (reference by id) is what makes aggregates independently loadable and independently shardable.
What I remember & apply
An aggregate is a consistency boundary, defined by an invariant → apply: name the invariant or reconsider the boundary.
Reference other aggregates by id only → apply: replace object references with id fields; it forces explicit loading.
One aggregate per transaction → apply: if you need two, use a domain event and eventual consistency.
Large aggregate = lock contention → apply: measure it; the design smell has a number.
