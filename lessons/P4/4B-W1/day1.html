Learn I — Requirements, capacity & the API

System Design & Architecture Practice · Phase 4 — DDD & Architecture · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Extracting non-functional requirementsNobody states them. You extract them by asking: how many users, how fast must it feel, what happens if it is down for an hour, does stale data cause harm, who must not see this data, what is the budget. Every one of those has an architectural consequence.
Availability arithmetic99% is 7.2 hours down per month. 99.9% is 43 minutes. 99.99% is 4.3 minutes — which means no human can respond in time, so it must be automatic. Each nine roughly multiplies cost. Asking 'which nine do you actually need' is often the highest-value question in a design discussion.
Numbers worth knowingMemory reference ~100ns; SSD random read ~100µs; network round trip within a datacentre ~0.5ms; cross-continent ~150ms (bounded by the speed of light — non-negotiable). A single well-tuned PostgreSQL node handles low thousands of simple transactions per second. These let you sanity-check any design in seconds.
API design essentialsResource-oriented URLs, correct verbs and status codes, RFC 9457 errors, cursor pagination for large or changing sets (offset pagination skips and repeats items when data changes underneath), and an explicit versioning strategy chosen before the first client integrates.
What I do
  1. Memorise the latency numbers and the availability-to-minutes conversions.
  2. Do design drill 1 — URL shortener — timed at 45 minutes using the framework.
  3. Do design drill 2 — rate limiter as a service — timed at 45 minutes.
  4. Write up both immediately afterwards, while the reasoning is fresh.
What I conclude
  • Capacity estimation is arithmetic, and being fluent at it makes you look — and be — much faster in design discussions.
  • Cursor pagination is correct for changing data; offset pagination is a bug waiting for the data to change.
  • The right availability target is a cost conversation, not a technical one.
What I remember & apply
99.9% = 43 min/month; 99.99% = 4.3 min → apply: above three nines, response must be automated.
Cross-continent RTT ~150ms is physics → apply: no architecture removes it; only placement does.
Cursor pagination for changing data → apply: offset pagination duplicates and skips rows under concurrent writes.
Extract NFRs by asking six questions → apply: users, speed, downtime cost, staleness, access, budget.
