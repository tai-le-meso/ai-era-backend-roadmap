What I learn
Search as a read modelFull-text search in PostgreSQL (tsvector, GIN index) is sufficient for a surprising range of needs and costs zero additional infrastructure. A dedicated search engine earns its place when you need relevance tuning, faceting, or scale beyond what one PostgreSQL node handles.
Feeding a read model from eventsThe search index is a projection: subscribe to domain events, update the index. Rebuildable, eventually consistent, and it keeps search concerns out of the write model.
Denormalisation trade-offsDenormalising speeds reads and creates update anomalies — the same fact in two places can diverge. In a read model fed by events that is acceptable because it is rebuildable; in a write model it is a correctness risk.
What I do
  1. Add a search read model to the flagship using PostgreSQL full-text search, fed by domain events.
  2. Implement rebuild-from-events for the search index.
  3. Write down what would justify moving to a dedicated search engine.
  4. Test the index stays consistent after a rebuild.
What I conclude
  • Starting with PostgreSQL full-text search and moving later is almost always cheaper than starting with a search cluster.
  • Denormalisation is safe in rebuildable read models and dangerous in write models.
What I remember & apply
PostgreSQL FTS handles more than people expect → apply: try it before adding a search cluster.
Read models rebuild from events → apply: makes denormalisation safe.
Write down the trigger for moving to dedicated search → apply: a documented threshold prevents premature migration.
