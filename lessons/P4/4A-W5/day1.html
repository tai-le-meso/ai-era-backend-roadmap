Learn I — Repositories, domain services, domain events & application services

Domain-Driven Design · Phase 4 — DDD & Architecture · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Repository as a collection abstractionA repository looks like an in-memory collection of aggregate roots: save, findById, remove. One repository per aggregate root — not per entity. A repository for a child entity means something outside the aggregate is loading it directly, which breaks the boundary.
Persistence ignorance vs JPA realityThe ideal is a domain model with no persistence annotations. The pragmatic reality in Spring is annotated entities. The compromise that works: keep persistence annotations but let no persistence concern (lazy loading decisions, flush timing, cascade semantics) influence a domain method's design.
Domain service vs application serviceA domain service holds logic that belongs to no single entity but is still business logic — TransferPolicy.canTransfer(from, to, amount). An application service orchestrates: opens the transaction, loads aggregates, calls domain methods, saves, publishes events. It contains no business rules. If you can describe an application-service method without using domain vocabulary, it is correct.
Domain events, raised inside, published after commitThe aggregate records an event when its state changes. The event is published after the transaction commits — @TransactionalEventListener(AFTER_COMMIT) — because publishing before commit can announce something that then rolls back. This connects to the outbox from 2C: the handler writes to the outbox.
What I do
  1. Read the Repository pattern definition and count how many of your repositories are per-entity rather than per-root.
  2. Classify every current 'service' class as domain or application service.
  3. Find every business rule that has leaked into a controller or a repository.
  4. Design the domain-event flow: raised in aggregate → published after commit → written to outbox.
What I conclude
  • One repository per aggregate root is the test of whether your aggregates are real.
  • An application service containing an if about business rules is a misplaced domain rule.
  • Publishing before commit is a correctness bug that only appears when transactions roll back.
What I remember & apply
One repository per aggregate root, never per entity → apply: extra repositories reveal boundary violations.
Application services orchestrate, domain services decide → apply: if you cannot describe it without domain terms, it is a domain service.
Publish domain events AFTER_COMMIT → apply: before-commit publication announces rollbacks as facts.
Domain event handler writes to the outbox → apply: joins the DDD model to the 2C delivery guarantee.
