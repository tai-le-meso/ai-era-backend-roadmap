What I learn
FactoriesWhen constructing an aggregate is complex — multiple invariants, derived values, external validation — a factory encapsulates it. A constructor that takes twelve arguments and validates six rules should be a factory method with a domain-meaningful name.
The specification patternEncapsulate a business predicate as an object: EligibleForOverdraft. It can be combined, tested independently, and reused in both domain logic and queries. Useful when the same rule appears in validation, selection, and reporting.
Enforcing the dependency rule with ArchUnitRules as tests: domain must not depend on infrastructure; application must not depend on the web layer; no class outside a module's internal package may be imported from another module. These run in CI and fail the build.
What I do
  1. Restructure: repositories only for aggregate roots.
  2. Extract TransferPolicy as a domain service.
  3. Strip all business logic out of application services.
  4. Write ArchUnit rules enforcing the dependency direction and run them in CI.
What I conclude
  • ArchUnit turns architecture from a document into a build gate — this is the single highest-leverage thing in this week.
  • Extracting a domain service usually reveals that the rule was duplicated in two places.
What I remember & apply
ArchUnit rules run in CI and fail the build → apply: write the dependency rule today; it prevents years of erosion.
Factories for complex construction → apply: a constructor validating six rules wants a named factory method.
Specification objects make rules reusable and testable → apply: use where the same predicate appears in logic and queries.
