Build the core — Retry, backoff & the retry storm

What I learn
Client-side vs server-side retryThe server can help by returning Retry-After and by distinguishing retryable (503, 429) from non-retryable (400, 422) failures. A client that retries a 400 is broken; a server that returns 500 for a validation error causes that.
Hedged requestsSend a duplicate request after p95 latency and take the first response. It cuts tail latency at the cost of extra load — only sane for idempotent reads with a strict tail-latency requirement.
What I do
  1. Ensure the flagship returns correct retryable vs non-retryable status codes.
  2. Add Retry-After to 429 and 503 responses.
  3. Document the amplification factor before and after in docs/reliability/.
  4. Commit the metrics screenshots as evidence.
What I conclude
  • Status-code discipline is a resilience feature: it tells clients what to do.
  • Hedging is a specialist tool; know it exists and know it costs load.
What I remember & apply
Retryable = 429, 503, timeouts; not-retryable = 4xx validation → apply: never return 500 for a validation error.
Retry-After on 429/503 → apply: it makes correct client backoff possible.
