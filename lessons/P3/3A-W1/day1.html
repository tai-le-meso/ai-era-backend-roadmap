Learn I — Failure models & timeouts

Reliability, Consistency & Coordination · Phase 3 — Distributed Systems · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
The fallacies, restated as design rulesThe network is not reliable, latency is not zero, bandwidth is not infinite, the network is not secure, topology changes, there is no single administrator, transport cost is not zero, the network is not homogeneous. Each fallacy maps to a design decision you either make deliberately or make by accident.
Partial failure is the defining problemIn a single process, a call either returns or throws. Across a network there is a third outcome: you do not know. The request may have succeeded, failed, or still be running. Every distributed design is fundamentally about handling that third case.
Timeouts: three different onesConnect timeout (establishing the socket), read/socket timeout (waiting for bytes), and total request timeout (the whole operation including retries). Setting only the socket timeout is the common half-measure — a response that trickles bytes slowly never trips it.
Timeout budgets and deadline propagationIf the client SLA is 500ms and you call three services, they cannot each have a 500ms timeout. The budget must be divided and the remaining deadline passed downstream, so a service that receives 80ms of budget does not start a 200ms operation.
The unbounded-queue antipatternA thread pool with an unbounded queue never rejects — it accumulates work until memory runs out, and every queued item is already past its deadline by the time it runs. Bounded queues plus explicit rejection turn a slow death into a fast, visible failure.
What I do
  1. Read the AWS timeouts/retries/jitter article end to end.
  2. Inventory every outbound call in the flagship: database, Redis, Kafka, HTTP.
  3. For each, record the current timeout — most will be 'none' or 'library default'.
  4. Compute the timeout budget: given a 500ms client SLA, what does each hop get?
What I conclude
  • 'No timeout' is the most common production bug and it is invisible until the day the dependency slows down.
  • A timeout without a budget is arbitrary; the budget is what makes the number defensible.
  • Unbounded queues convert overload into an outage instead of into backpressure.
What I remember & apply
Three timeouts: connect, read, total → apply: set all three; a read timeout alone does not bound a slow trickle.
Propagate the remaining deadline downstream → apply: pass it as a header and check it before starting work.
Unbounded queue = deferred OOM → apply: every executor gets a bounded queue and a rejection policy.
Partial failure means 'unknown' is a real outcome → apply: design the unknown path explicitly (it becomes 5B's UNKNOWN payment state).
