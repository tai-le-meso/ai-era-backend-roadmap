What I learn
Read-after-write violations in practiceUser updates their address, the read goes to a lagging replica, and the old address comes back. It looks like the save failed. Fixes: route reads to the primary for N seconds after a write; pin the session to the primary; or carry a write token (LSN) and require the replica to have caught up to it.
Monotonic readsTwo consecutive reads hitting different replicas with different lag can show time going backwards. Sticky routing to one replica per session fixes it cheaply.
Conflict resolutionLast-write-wins silently discards data and depends on clock accuracy. Vector clocks detect concurrency instead of guessing. CRDTs converge by construction for specific data types (counters, sets) — powerful where they fit, not general.
What I do
  1. Build the demo that visibly violates read-your-writes via the replica.
  2. Implement all three fixes and measure their cost.
  3. Extend to a monotonic-reads violation across two replicas and fix with sticky routing.
  4. Record which fix you would ship and why.
What I conclude
  • Read-after-write is the violation users notice first and report as 'it didn't save'.
  • Last-write-wins is data loss with a friendly name.
What I remember & apply
Fix read-after-write with sticky-primary, session pinning, or an LSN token → apply: pick per read path, not globally.
Monotonic reads break across replicas with different lag → apply: sticky-session routing is the cheap fix.
LWW discards data and trusts clocks → apply: never use it for anything a user would miss.
