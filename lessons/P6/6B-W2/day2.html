What I learn
Semantic cache correctness riskTwo prompts with high embedding similarity can require different answers — 'what is my balance' and 'what was my balance last month' may embed closely. A false hit returns a confidently wrong answer with no error anywhere. The similarity threshold is a correctness parameter, and it must be tuned against real data.
Measuring the false-hit rateSample cache hits, check whether the cached answer is actually correct for the new query, and compute the rate. This number decides whether the cache is usable at all in your domain.
Where caching must be disabledAnything personalised, anything where the answer depends on current data (balances, limits, statuses), and anything with an audit requirement where the response must be freshly derived.
What I do
  1. Implement a semantic cache with a tunable similarity threshold.
  2. Measure the false-hit rate at several thresholds on real queries.
  3. Define and enforce the list of paths where caching is disabled entirely.
  4. Measure cost per request before and after all optimisations.
What I conclude
  • A semantic cache is the only optimisation in this week that can produce wrong answers — treat its threshold as a correctness parameter.
  • In banking, most personalised queries must bypass the cache entirely.
What I remember & apply
Semantic cache false hits return confidently wrong answers → apply: measure the rate before enabling it.
Disable caching for personalised, current-data and audited paths → apply: maintain an explicit no-cache list.
Tune the similarity threshold on real queries → apply: a default threshold is a guess about your domain.
