What I learn
Measuring recallFor a sample of queries, compute exact top-k and approximate top-k, and measure the overlap. Recall@10 of 0.85 means you are missing 15% of the true best results — which may be fine for browsing and unacceptable for compliance search.
Metadata filtering: pre vs postPost-filtering retrieves top-k by vector similarity then discards non-matching rows — so a restrictive filter can leave you with almost nothing. Pre-filtering restricts the candidate set first, which is correct but can defeat the index unless it is designed for it. In pgvector, partial indexes and careful query structure are how you handle common filters.
Multi-tenancy in a vector storeTenant isolation must be a pre-filter, not a post-filter — otherwise you retrieve another tenant's documents and then discard them, which is both wrong and a data-leak risk if anything logs the intermediate results.
What I do
  1. Measure recall@10 for both indexes at several parameter settings.
  2. Implement tenant-scoped retrieval as a pre-filter, with a partial index if needed.
  3. Test that a restrictive filter does not silently return near-empty results.
  4. Write a test proving cross-tenant retrieval is impossible.
What I conclude
  • Post-filtering with a restrictive predicate quietly returns fewer results than requested — a silent quality failure.
  • Tenant filtering must be structural, exactly as in 4B multi-tenancy.
What I remember & apply
Post-filter + restrictive predicate = near-empty results → apply: pre-filter, and test with your most restrictive filter.
Tenant scoping must be a pre-filter → apply: it is both a correctness and a security requirement.
Measure recall@k at several parameter settings → apply: pick the setting from the curve, not the default.
