Learn I — The AI Gateway

AI Backend Architecture · Phase 6 — AI Application Engineering · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Why a gatewayOne place for auth, quota, routing, caching, logging, cost attribution and safety. Without it every service reimplements them, inconsistently, and you cannot answer 'what did we spend on AI last month, by team' at all.
Provider abstraction without lowest-common-denominatorProviders differ in streaming format, tool-calling shape, caching semantics and system-prompt handling. A naive abstraction hides the differences and loses the features. A good one exposes a common core plus explicit capability flags, so callers can use provider-specific features knowingly.
Streaming proxyingServer-sent events through a proxy need careful buffering — buffer too much and you destroy TTFT, the main reason to stream. Backpressure matters: if the client is slow, the proxy must not accumulate unbounded chunks in memory.
Cancellation propagationWhen a client disconnects mid-stream, the upstream call must be cancelled — otherwise you pay for tokens nobody receives. This is easy to get wrong and directly visible in the bill.
What I do
  1. Design the gateway's interface: provider-agnostic core plus capability flags.
  2. Implement per-tenant authentication and quota at the gateway.
  3. Implement streaming passthrough with bounded buffering.
  4. Implement cancellation propagation on client disconnect and verify tokens stop being billed.
What I conclude
  • A gateway's value is centralising the concerns that are painful to retrofit: cost attribution, quota and safety.
  • Cancellation propagation is a cost control that most implementations miss.
What I remember & apply
Gateway centralises auth, quota, routing, caching, logging, cost, safety → apply: it is the only place these can be consistent.
Expose capability flags, don't hide provider differences → apply: lowest-common-denominator abstractions lose the good features.
Bound streaming buffers → apply: unbounded buffering on a slow client is a memory leak.
Propagate cancellation upstream → apply: otherwise you pay for tokens after the client left.
