Session 1 — Learn I~4.5h
Objective: understand the first half of this block's theory well enough to explain it without notes.
0:00–2:00Primary sources — docs, book chapter, or the actual source code. No videos.
2:00–3:30Second source or hands-on exploration of the same topics (REPL, scratch project, EXPLAIN, jshell — whatever fits).
3:30–4:30Write notes in your own words. If you can only copy, you haven't understood it yet.

Topics for today

  • Context construction: ordering, deduplication, token budgeting, what to drop first.
  • Citation and grounding: forcing source attribution, verifying citations actually support the claim, refusing when context is insufficient (the single most valuable behaviour in a regulated domain).
  • Handling conflicting sources.
Artifact: notes page committed to logs/. End-of-day question: which of today's topics could you not yet explain to a junior?
Session 2 — Learn II → Design~4.5h
Objective: finish the theory, then design this block's build before writing any real code.
0:00–1:30Remaining theory (below).
1:30–2:30Design: sketch the approach, decide the tests, name the risks. Ten minutes of diagram beats an hour of rework.
2:30–4:30Scaffold and start: branch, skeleton, first failing test.

Remaining topics

  • Freshness and incremental re-indexing.
  • Access control in retrieval — never retrieve documents the user cannot see (the most common serious RAG security bug).

Design target

Ship v6: the full RAG path User → API → Retrieval → LLM → Structured Response with per-user access-scoped retrieval, enforced citations, a verification step that checks each citation supports its claim, and an explicit refusal path.

Artifact: design note + branch with a failing test. End-of-day question: what is the riskiest assumption in your design?
Session 3 — Build the core~4.5h
Objective: the hardest part working, with tests. Hardest first — while energy is highest.
0:00–4:00Deep build. Phone in another room.
4:00–4:30Commit; write down blockers for tomorrow.

Build tasks

Primary task: Ship v6: the full RAG path User → API → Retrieval → LLM → Structured Response with per-user access-scoped retrieval, enforced citations, a verification step that checks each citation supports its claim, and an explicit refusal path.

  • Write a test proving a user cannot retrieve another tenant's documents.
Artifact: core implementation committed with passing tests. End-of-day question: what would break this under concurrent load?
Session 4 — Finish · Measure · Reason · AI~4.5h
Objective: ship the deliverable, then do the thinking that turns the week into senior-level judgment.
0:00–1:30Finish the build: edge cases, break it deliberately, measure.
1:30–3:00Reason (written — never skip): How do you prove an answer was grounded? What is your refusal rate and is it too low (over-confident) or too high (useless)? What is the audit trail for an AI-generated answer in a bank?
3:00–4:30AI drill: Try to make your own system produce an ungrounded confident answer. Every success is a bug to fix. Then log what you accepted, rejected, and why.
Artifact: v6 tagged + access-control test + citation verification.

Block gate — do not move on until

  • Deliverable shipped: v6 tagged + access-control test + citation verification.
  • Self-check passes: My retrieval is access-scoped and I have a test proving it.
  • Ticked in the roadmap tracker (and progress exported).

Behind? Push the schedule, not the quality — an unshipped deliverable means the block is not done.
