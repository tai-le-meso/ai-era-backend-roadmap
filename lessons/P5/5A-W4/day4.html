What I learn
Who wins the fraction is policyEvery rounding and allocation sends fractions of a cent somewhere — to the customer, the bank, or a rounding-difference GL account. At scale this is real revenue (the classic 'salami' fraud is exactly harvesting it silently), so the direction must be a documented product/finance decision, and a rounding-residue account makes the aggregate visible and auditable.
AI reliably fumbles allocationTypical failures: divide-then-round losing cents, floating-point intermediates, ignoring 0/3-decimal currencies, non-deterministic remainder distribution. Your property test is the objective judge — run generated code through it rather than eyeballing.
What I do
  1. Run the drill: have AI implement money allocation, then run your jqwik property suite against its code; document each failure mode found.
  2. Trace one flagship flow (e.g. fee + FX) and identify where rounding residue goes today; route it explicitly (policy + rounding GL account) if it is accidental.
  3. Commit deliverables: Money type, allocation property test, FX with rate provenance.
  4. Self-check: explain banker's rounding and one context where a regulation or scheme fixes the rounding rule.
What I conclude
  • Fractions must land somewhere deliberate and observable — an explicit rounding account converts a fraud vector into a monitored number.
  • Property tests are how you safely use AI for money code: generated implementation, human-owned invariants.
What I remember & apply
Route rounding residue to a dedicated GL account with a policy note → apply: chart of accounts update this week.
Salami-slicing = harvesting rounding fractions; visibility is the defence → apply: recon/monitoring rules in 5A-W6 and 5B-W4.
Judge AI money code by running invariant suites, not by reading it → apply: standing practice for all Phase-5 drills.
