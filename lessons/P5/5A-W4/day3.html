Build the core — Money, monetary precision & currency

Banking Domain & Ledger Engineering · Phase 5 — Fintech / Core Banking · ~4.5h
Day 1Day 2Day 3 — Build the coreDay 4↑ Week overview
What I learn
Property tests for moneyProperties to assert with jqwik: allocate(n) sums exactly to the original for any amount/n; each part within one minor unit of fair share; allocation is deterministic; add/subtract round-trip; scale always equals the currency's minor units. Generators: random amounts across currencies including JPY and BHD, n from 1 to 1000, random weight vectors.
Where rounding happens is architecturalRound once, at the boundary where a value becomes real money (a posted entry, a customer display), never mid-calculation. Keep intermediate FX/interest math at higher precision (MathContext), then apply the currency's rounding at posting time — and record who received the remainder.
What I do
  1. Implement Money (immutable, currency-scale-normalised, HALF_EVEN default) with add/subtract/compare, allocate(n) and allocate(weights).
  2. Implement FxConversion and a convert() that returns Money plus the conversion record; persist rate provenance on the ledger entry.
  3. Write jqwik properties: no cent created or lost across random allocations (all currencies, including 0- and 3-decimal); conversion provenance always present.
  4. Add multi-currency account support: one position per currency, no cross-currency totals in the domain layer.
What I conclude
  • The allocation property test is the money analogue of the trial-balance property — cheap to write, catches an entire bug class forever.
  • High-precision intermediates + single boundary rounding gives reproducible numbers and a nameable fraction-winner.
What I remember & apply
Round once at the posting/display boundary; intermediates keep extra precision → apply: interest and FX pipelines in the flagship.
Property: sum(allocate(m, n)) == m for all m, n, currency → apply: run it against AI-generated code on day 4.
Multi-currency account = map currency→position; totals are report-time projections → apply: balance API extension.
