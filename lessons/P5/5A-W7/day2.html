What I learn
Event sourcing — where it genuinely fitsA double-entry journal is already an event-sourced system for money: append-only facts, state (balances) as projections, rebuild capability. That is why the ledger is one of the few places ES pays: the domain's regulatory model IS the event log. Extending ES to the whole application (customers, products) buys complexity without the same payoff — be able to argue both halves.
Segregation of duties and maker-checkerSoD: the person who initiates must not be the person who approves; neither should be able to alter the audit record of either action. Maker-checker (four-eyes): high-value/high-risk operations create a PENDING_APPROVAL intent; a different principal approves or rejects; the approval itself is an audited event carrying both identities. Enforce 'maker ≠ checker' in code AND at the data layer.
Data lineageFor any reported number, lineage answers: which entries, which rules/versions, which transformations produced it. Practically: report rows carry the entry-id set (or a query + as-of pair) that generated them, and ruleset versions are part of the recon/report run metadata (as built in W6). BCBS 239's accuracy/completeness principles are the regulatory statement of this requirement.
What I do
  1. Read Fowler's Event Sourcing critically; write the two-paragraph position: why ES fits the ledger, why you would not event-source the whole flagship.
  2. Skim BCBS 239 principles 3–6 (accuracy, integrity, completeness, timeliness) and map each to a concrete mechanism you have built in 5A.
  3. Design maker-checker: approval entity, state flow, maker≠checker invariant, threshold policy (which operations require it).
  4. Design the point-in-time balance report: inputs (account, date D, knowledge date T), outputs (balance + contributing entries + snapshot lineage), all reusing the W5 as-of query.
What I conclude
  • The ledger is event sourcing done by accountants 700 years early — projections (balances) plus replay (rebuild) complete the pattern.
  • Maker-checker converts 'we trust our staff' into 'we can prove no single person could do this' — which is what the regulator is actually asking.
  • Lineage is cheap if carried along (ids + versions on every derived artifact) and brutally expensive to reconstruct afterwards.
What I remember & apply
Ledger = events; balances = projections; rebuild = replay → apply: frame the v5 README this way.
Maker ≠ checker enforced in code and data, approval is itself an audited event → apply: day-3 build for high-value operations.
Every derived report carries entry-ids + ruleset version + as-of pair → apply: regulator report tomorrow.
BCBS 239 accuracy/completeness/timeliness = the 'why' for rebuildability and lineage → apply: cite it in the design doc.
