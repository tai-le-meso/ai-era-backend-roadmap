What I learn
What an audit trail must answerWho (authenticated principal, not a service account alias), did what (operation + before/after values), when (trusted timestamp), from where (origin/channel), and under what authority (approval reference). If any of the five is reconstructed from application logs instead of first-class data, it will be incomplete exactly when it matters.
Hash chaining for tamper evidenceEach audit record stores hash(prev_hash || canonical(record)); modifying or deleting any historical record breaks every subsequent hash. This makes tampering DETECTABLE, not impossible — an insider who can rewrite the whole chain defeats it, so anchor periodic checkpoint hashes externally (WORM bucket, printed in reports, or a Merkle root per RFC 6962). Canonicalisation (stable field order/encoding) is where most implementations break.
WORM storage and retentionWrite-once-read-many storage (e.g. object-lock/compliance-mode buckets) enforces immutability at the infrastructure layer for the 7–10 year financial retention horizon. Retention that long makes format durability (plain JSON/CSV over bespoke binary), key management (5B-W5) and 'can we still read 2019's archive' tests real engineering concerns.
What I do
  1. Read RFC 6962's Merkle tree section; write half a page on hash chain vs Merkle tree (linear verification vs O(log n) inclusion proofs) and pick your design.
  2. Define the audit record schema: actor, operation, entity, before/after, timestamp, origin, approval_ref, prev_hash, hash — with canonical serialisation rules written down.
  3. Re-read Square's Books post noting every audit-relevant choice (append-only, corrections, balance-to-zero).
  4. Decide the external anchoring cadence for checkpoint hashes and where they will live.
What I conclude
  • Tamper-evident ≠ tamper-proof: the chain detects, the external anchor prevents silent whole-chain rewrites.
  • Audit data is first-class domain data with a schema and tests — never 'whatever ended up in the log aggregator'.
  • Canonical serialisation is a contract; changing JSON field order must not break historical verification.
What I remember & apply
hash_n = H(hash_{n-1} || canonical(record_n)); any historical edit cascades failures forward → apply: day-3 verification job.
Anchor checkpoint hashes outside the mutable system (WORM/external) → apply: v5 design decision today.
Retention 7–10y in finance: choose boring durable formats and test old-archive readability → apply: archive job + annual restore test.
Audit answers who/what/when/where/authority as structured fields → apply: audit-trail query API on day 3.
