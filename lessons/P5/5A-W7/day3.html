What I learn
Verification as a scheduled controlThe tamper-check job re-walks the chain from the last externally anchored checkpoint, recomputing hashes; a mismatch names the first broken record. Run it on schedule, alert on failure, and test it by actually tampering in a test environment — an unexercised control is decoration.
The regulator-ready report'Prove this balance was correct on 30 June' = one command producing: the as-of balance, the contributing journal entries, the reversal/adjustment chains touching them, the audit records for each, and the chain-verification status — generated in minutes, not 'I'd write a query'. Build the report; the build forces every gap into the open.
What I do
  1. Implement the hash-chained audit log (interceptor/decorator on state-changing operations) + the verification job; test it by tampering with a row and asserting detection names the right record.
  2. Implement maker-checker for high-value operations with maker≠checker tests.
  3. Implement the audit-trail query API (by entity, by actor, by period) and the point-in-time balance report command.
  4. Tag v5.
What I conclude
  • Controls must be exercised: the tamper test that actually tampers is the difference between security theatre and evidence.
  • If producing the proof takes minutes, audits are cheap; if it takes a war room, every audit is an incident.
What I remember & apply
Verification job re-walks from the last external anchor and names the first bad record → apply: wire the alert to on-call.
Test controls by violating them in test (tamper a row, attempt self-approval) → apply: CI suite for v5.
Point-in-time proof = as-of balance + entries + corrections + audit records + chain status, one command → apply: the deliverable and the 5B-W6 risk-officer drill.
