Learn I — Transaction lifecycle, reversal & adjustment

Banking Domain & Ledger Engineering · Phase 5 — Fintech / Core Banking · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
The transaction lifecycleinitiated → authorised (funds reserved, hold on available balance) → captured (amount finalised, possibly partial) → settled (money irrevocably moved, posted to ledger) → and off-ramps: failed, expired (hold lapsed), reversed. Each transition has an owner (customer, merchant, scheme, clock) and only some are legal — encode them as a sealed-type state machine so illegal transitions don't compile.
Cancellation vs reversal vs adjustmentCancellation happens BEFORE posting: the instruction dies, no ledger entry ever exists (Stripe: cancel an uncaptured PaymentIntent — free). Reversal happens AFTER posting: a new compensating entry with debits and credits swapped, linked to the original; both remain forever. Adjustment corrects a wrong amount: either reverse-and-repost or post the difference — also strictly additive.
Partial operationsPartial capture settles less than authorised (hold residue releases); partial refund reverses part of a settled amount (multiple refunds allowed, sum ≤ original); chargeback is a scheme-initiated reversal with its own dispute lifecycle and a fee, not something you 'accept' in your own state machine — model it as an inbound event.
What I do
  1. Read Stripe's refunds page; table the differences: cancel vs refund vs reversal, when each is possible, what it costs.
  2. Re-read TigerBeetle two-phase transfers; map pending/post/void/expire to authorise/capture/cancel/expire.
  3. Draw the full state diagram with owners on each transition and mark which states have ledger entries.
  4. List the legal-transition matrix and turn it into parameterised tests before writing the machine.
What I conclude
  • The ledger only knows settled facts and compensations; the richer lifecycle lives in the payment domain above it.
  • 'Can this still be cancelled?' is exactly 'has it posted?' — the posting moment is the point of no return for edits.
  • Chargebacks arrive from outside; your model consumes them, it does not gate them.
What I remember & apply
Cancel = before posting, nothing booked; reverse = after posting, compensating entry; adjust = correcting entry → apply: API naming and the day-4 auditor explanation.
Partial capture releases the hold residue; sum(refunds) ≤ captured amount → apply: invariants in the day-3 state machine.
Every off-ramp (failed/expired/reversed) is a terminal state with a reason code → apply: customer status mapping in 5B-W2.
Chargeback = externally initiated reversal event with dispute workflow → apply: 5B-W1 card-rail adapter semantics.
