Payments, Compliance & Risk · Phase 5 — Fintech / Core Banking · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Fee models and timingFixed, percentage, tiered (marginal vs slab — specify which!), and blended models; charged upfront, on settlement, or aggregated monthly. Wire fees carry OUR/SHA/BEN: OUR = sender pays all charges, BEN = beneficiary pays (amount arrives reduced), SHA = each side pays its own — this determines whether the beneficiary receives the instructed amount and where fee entries post. On refund, decide per fee whether it returns (usually the fee does not, or partially — a product policy your engine must encode).
Fee versioning is a correctness requirementFees change; old transactions keep the terms in force when they executed. So the engine stores fee schedules as versioned, effective-dated data, and each transaction records WHICH schedule version priced it — reprice-on-read is a bug that rewrites history (same principle as the 5A-W5 append-only rule).
Limits as authorisation invariantsPer-transaction, daily/monthly cumulative, velocity (N per window), per-channel, per-risk-tier. A limit check is only meaningful inside the same transactional boundary as the reservation it guards: check-then-reserve as two independent steps is a TOCTOU race. Under READ COMMITTED, two concurrent 600-payments both read 'spent 0 of 1000', both pass, and together breach — the fix is serialising on the limit counter: SELECT...FOR UPDATE on a counter row, an atomic conditional UPDATE (spent + x <= limit), or SERIALIZABLE with retry.
What I do
  1. Write the fee-engine model: FeeSchedule (versioned, effective-dated), FeeRule (model type, params), FeeApplication (transaction id, schedule version, computed amount) — with the 5A-W4 allocation for percentage fees.
  2. Table the OUR/SHA/BEN cases: who pays, what amount arrives, which ledger entries post where.
  3. Re-read PostgreSQL isolation and write the exact interleaving where two concurrent transactions breach a daily limit under READ COMMITTED.
  4. Choose your race-proofing mechanism (FOR UPDATE counter row vs atomic conditional update vs SERIALIZABLE) and justify it in one paragraph including the hot-account implications from 5A-W3.
What I conclude
  • Fee computation is a pure function of (transaction, schedule-version); persistence of the version is what makes old transactions immutable in meaning.
  • A limit check outside the reservation's transactional boundary is decorative — the race window is exactly the gap between check and reserve.
  • OUR/SHA/BEN is why 'the amount that arrives' ≠ 'the amount instructed' — recon (5A-W6) must expect it.
What I remember & apply
Transactions store the fee-schedule version that priced them; never reprice history → apply: fee engine schema on day 3.
SHA = each side pays own fees (SEPA default); BEN = amount arrives reduced → apply: expected-amount logic in recon matching.
Two concurrent passes under READ COMMITTED can jointly breach a limit; serialise on the counter → apply: the day-3 race test.
Velocity limits need a windowed counter with the same race-proofing → apply: same mechanism, different key.
