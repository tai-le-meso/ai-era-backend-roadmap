What I learn
Composing the authorisation pipelineOne transactional unit: risk decision (may exit to step-up) → limit reservation (race-proof) → fee computation (versioned) → hold/posting. Order matters: risk before limits (don't consume limit budget on payments risk will kill), fees computed before posting so the entry set is complete. If the rail submission later fails, the saga's compensation releases the limit reservation — limits are reserved-then-confirmed, like money.
Proving race-freedomThe test: two concurrent payments that individually pass but jointly breach, fired simultaneously (CyclicBarrier/CountDownLatch across threads against the real database, repeated N times); assert exactly one succeeds. A passing test under real concurrency is your 'I can prove it' for the week's check.
What I do
  1. Implement the versioned fee engine including refund-fee policy and allocation-based percentage fees.
  2. Implement the limits engine with your chosen serialisation mechanism, participating in the same DB transaction as the hold/posting; include reservation-release compensation.
  3. Implement the rule-based risk scorer with the decision-audit log and allow/step-up/deny outcomes wired into the saga.
  4. Write the concurrent-breach test (barrier-synchronised, repeated) and the fee-versioning test (change schedule, assert old transaction keeps old terms).
What I conclude
  • Limits are a reservable resource like money: reserve, confirm, or release — the same saga discipline applies.
  • Race-proofing lives in the database's transactional semantics, not in application-level checks; test it with real concurrency, not mocks.
What I remember & apply
Pipeline order: risk → limits → fees → posting, one transactional boundary for check+reserve → apply: saga step wiring today.
Limit reservations need compensation on downstream failure → apply: saga compensation list.
Barrier-synchronised concurrent tests against the real DB are the only honest race tests → apply: today's proof and CI.
