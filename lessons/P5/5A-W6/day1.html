Learn I — Reconciliation

Banking Domain & Ledger Engineering · Phase 5 — Fintech / Core Banking · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Why reconciliation existsTwo systems recording the same money WILL disagree — lost messages, timing, duplicates, bugs, fraud. Reconciliation is the control that bounds how long a disagreement can live. Internal recon proves sub-ledger totals equal GL control accounts; external recon proves your ledger equals the bank/scheme statement. It is a product feature with SLAs and UI, not a cron script someone owns informally.
Matching strategiesExact match: same reference + amount + date. Fuzzy: tolerant of date windows (±2 days), truncated references, transformed descriptions. One-to-many: one statement line vs many ledger entries (batch settlement of N payments); many-to-many: netted settlements vs gross entries. Match confidence should be scored, with auto-match above a threshold and a review queue below it.
Break categories and what each meansTiming difference: we posted, they haven't (or vice versa) — normal, self-heals within a window. Missing: past the window, present on one side only — lost message or data loss BUG. Duplicate: same economic event twice — idempotency failure. Amount mismatch: fee/FX/rounding difference or a money bug. The category determines urgency: timing is ops-normal; missing and duplicate are engineering incidents.
What I do
  1. Read both Modern Treasury pieces; write your flagship's recon inventory: which pairs of systems, which direction is source-of-truth, at what cadence.
  2. Define the break taxonomy enum (TIMING, MISSING_INTERNAL, MISSING_EXTERNAL, DUPLICATE, AMOUNT_MISMATCH) with an SLA and severity per category.
  3. Sketch matching keys for your data: what reference travels end-to-end today? If none does, that is finding #1 — fix the payment flow to carry one.
  4. Hand-reconcile 10 fabricated statement lines against 10 ledger entries containing one break of each category.
What I conclude
  • Reconciliation is where every other system's silent bug becomes visible — a data-loss bug shows up here first, as a MISSING break that never self-heals.
  • Matching quality is determined upstream: an end-to-end reference carried through the payment flow is worth more than any fuzzy algorithm.
  • Break category, not break count, drives response: 1000 timing breaks are Tuesday; 1 duplicate is an incident.
What I remember & apply
Break taxonomy: timing / missing / duplicate / amount-mismatch, each with its own SLA → apply: day-3 classifier and alerting rules.
One-to-many matching is the norm for batch rails (one settlement line, N payments) → apply: matcher design for the ACH/SEPA adapters of 5B-W1.
End-to-end reference propagation is the #1 recon enabler → apply: add/verify a reference field through the whole flagship payment path.
MISSING past the timing window = probable data loss; page engineering, not ops → apply: severity mapping in the break API.
