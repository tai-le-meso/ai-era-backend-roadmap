What I learn
Compliance module shapeThree ports, one principle: KYC status gates the saga's validation step; screening is called at onboarding and inside the payment pipeline (before rail submission — a hit must stop money, not report it later); monitoring consumes the settled-transaction stream asynchronously and raises cases. All three write decision logs referencing rule/list versions (the 5A-W7 audit substrate).
Fuzzy matching pragmaticsPipeline: normalise (case, diacritics, punctuation) → token sort → phonetic encoding and/or edit-distance score against candidate names → weighted score vs thresholds. Two thresholds create three outcomes: auto-clear below, auto-hit above, review between. Tune with a labelled test set and measure both error directions — same FP/FN discipline as 5A-W6 recon.
What I do
  1. Implement KYC status gating in the payment saga's validation step (blocked/unverified cannot send; test it).
  2. Implement the screening port with the normalise→score→threshold pipeline, review queue, and decision log with list version; unit-test with your day-2 alias examples.
  3. Implement one monitoring rule (structuring: N transactions under threshold X within window W across an account cluster) raising a case with need-to-know access.
  4. Tokenise all card-like data in the flagship; verify by grep/test that no PAN-shaped data exists outside the vault.
What I conclude
  • Screening sits synchronously in the money path; monitoring sits asynchronously behind it — placement follows whether the control must PREVENT or DETECT.
  • A tokenisation claim is testable: scan storage and logs for PAN patterns and make the scan a CI check.
What I remember & apply
Prevent-controls (screening, KYC gates, limits) are synchronous; detect-controls (monitoring) are async → apply: pipeline placement in any future fintech design.
Two-threshold screening: clear / review / hit → apply: same triage shape as recon matching.
PAN-pattern scanning of DBs and logs as an automated test → apply: CI job committed today.
