What I learn
Crypto-shredding architecturePer-subject data-encryption keys (DEKs) in a key store, envelope-encrypted by rotating master keys (KEKs) in a KMS/HSM. Personal fields encrypt under the subject's DEK wherever they live — events, rows, files, backups become unreadable together when the DEK is destroyed. Ledger entries reference subject_id (a pseudonym) and keep amounts/dates/accounts in plaintext: money facts reconcile forever; identity evaporates on shred. Backups are the killer detail: keys must NOT live in the same backup stream as data, or 'destroyed' keys resurrect on restore.
Honest limits of crypto-shreddingVerraes' own update: encrypted personal data is still personal data while the key exists, and some regulators may not accept key-destruction as erasure in all cases — so treat crypto-shredding as an engineering mechanism whose sufficiency is confirmed with your DPO, and pair it with data minimisation (don't collect what you'd have to shred). Alternative for high-sensitivity fields: forgettable payloads (store the data outside the event/ledger, reference it, hard-delete the referent).
Keys over a 10-year horizonRetention outlives algorithms, staff, and cloud contracts. You need: KEK rotation (re-wrap DEKs, don't re-encrypt data), crypto-agility (algorithm field per ciphertext for future migration), key-usage audit (who unwrapped what, when — feeding the W7 audit log), and shred evidence (destruction event recorded, itself retained).
What I do
  1. Read the Verraes pattern including the legal-caveat update, then the event-driven.io strategy menu; write a half-page decision: which strategy for which field class in the flagship.
  2. Design the key hierarchy: per-subject DEK, KEK envelope, storage separation (keys in KMS, never in data backups), rotation procedure.
  3. Design the erasure flow: verify request → check legal-basis retentions → destroy DEK → record shred event → verify unreadability.
  4. Write the test plan: after erasure, (1) personal fields unreadable, (2) ledger trial balance still zero, (3) recon of affected accounts still passes, (4) audit chain (5A-W7) still verifies.
What I conclude
  • Crypto-shredding's power is covering every copy at once — including backups — exactly because it deletes readability, not rows.
  • Key-management hygiene IS the erasure guarantee: keys in the data backup stream silently void the whole design.
  • Minimisation beats shredding: the cheapest personal data to erase is the field you never collected.
What I remember & apply
Erasure = destroy per-subject DEK; ledger keeps pseudonymous financial facts and still balances → apply: day-3 build and the erasure-preserves-reconciliation test.
Keys and data in separate backup streams, or restores resurrect 'erased' data → apply: infrastructure review this week.
Record the shred event as audit evidence (what, when, who, why) → apply: hash-chained audit log from 5A-W7.
Crypto-shredding sufficiency is a DPO conversation, not an engineering assumption → apply: flag it in the day-4 write-up.
