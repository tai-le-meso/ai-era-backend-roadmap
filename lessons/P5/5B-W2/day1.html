What I learn
The full payment state machineinitiated → validated → risk_checked → authorised → captured → sent → settled, with off-ramps returned, reversed, failed, expired — plus the state this week exists for: UNKNOWN. Distinguish retry (same instruction, safe only with idempotency), reversal (we compensate our own posted entry), and return (the counterparty/scheme sends it back). Each is triggered by a different party and lands in a different state.
The unknown-outcome problemYou sent the payment; the response never came (timeout, connection reset, process crash). The payment is in exactly one of {succeeded, failed, never-arrived} at the partner — but you cannot know which from your side. Blind retry risks a double-send (a real double-spend of customer money); doing nothing strands the customer. UNKNOWN must be an explicit, first-class state with an exit procedure, not an exception swallowed into 'failed'.
Cut-offs, batch windows, mandatesBatch rails accept until a cut-off, then nothing moves until the next cycle — 'processing' can honestly mean 'waiting for 07:00'. Recurring payments rest on mandates (authorisation to debit, e.g. SEPA Direct Debit mandates) with their own lifecycle (setup, amendment, cancellation) and scheduled execution that must respect calendars and cut-offs.
What I do
  1. Read the Stripe idempotency post; write the three-step client protocol (key generation, retry with same key, backoff+jitter).
  2. Draw the full state machine including UNKNOWN with its entry condition (timeout/lost response) and its two exits (confirmed-success, confirmed-failure).
  3. Write the decision table: for each failure signal (synchronous reject, timeout, async return, partner 500), is the correct action retry / reverse / return-handling / enquiry?
  4. Read the EPC SCT page's R-transaction and inquiry material; add scheme names (recall, return, reject) to the table.
What I conclude
  • Timeout is not failure — it is absence of information; encoding that distinction as an UNKNOWN state is the core design move of payment orchestration.
  • Retry, reversal and return are different words because different parties act — a decision table prevents ops improvisation at 2am.
  • Cut-off calendars are domain data (per rail, per partner), not configuration trivia.
What I remember & apply
UNKNOWN = sent, outcome unconfirmed; exits only via status enquiry or reconciliation → apply: day-3 saga implementation.
Blind retry after timeout = potential double-spend; retry only with the same idempotency key → apply: the drill on day 4.
Retry (us, same instruction) vs reversal (us, compensate) vs return (them) → apply: ops runbook and API naming.
Mandate = stored authorisation with its own lifecycle → apply: recurring-payment model in the flagship.
