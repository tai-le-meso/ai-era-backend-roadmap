What I learn
Idempotency end-to-endThe key is generated at the EDGE (client/first service) and travels the whole chain: API → orchestrator → rail adapter → partner. TigerBeetle's guidance generalises: persist the ID before first send, reuse it on every retry, and let the receiving side answer 'exists' instead of duplicating. A key that is generated fresh per retry is worthless.
Resolving UNKNOWN, two waysActive: status enquiry — poll the partner's status API or send the scheme's status/inquiry message (pacs.002 answers; camt.056 requests cancellation/recall) on a backoff schedule with a deadline. Passive: reconciliation-driven — the settlement file/statement (W6 recon) eventually proves whether the payment exists at the partner. Production systems need both: enquiry for minutes-scale resolution, recon as the backstop that always terminates.
Saga shape for a paymentSteps: reserve funds (hold) → risk/limits → submit to rail → await confirmation → post settlement + release hold; compensations: void hold, reverse posting. The UNKNOWN branch parks the saga (funds still held — deliberately), schedules the enquiry poller, and forbids compensation until the outcome is known: compensating while the partner actually succeeded is itself a double-spend.
What I do
  1. Read TigerBeetle's reliable-submission page; write your ID-flow diagram: who generates, where persisted, how far it propagates.
  2. Locate pacs.002 and camt.056 on iso20022.org and note the status codes pacs.002 can carry (accepted/rejected/pending).
  3. Design the saga: steps, compensations, the UNKNOWN parking state, poller schedule with deadline, and the recon-resolution hook.
  4. Decide and document what the customer sees during UNKNOWN (amount deducted-pending, honest 'confirming with your bank' copy, no cancel button).
What I conclude
  • Idempotency keys + status enquiry + reconciliation backstop is the complete exactly-once illusion over an at-least-once world.
  • During UNKNOWN, keep the hold: releasing customer funds before the outcome is known converts uncertainty into real double-spend risk.
  • Never auto-compensate an UNKNOWN — compensation is only safe against a KNOWN failure.
What I remember & apply
Idempotency key: edge-generated, persisted before send, constant across retries → apply: API contract + saga tables on day 3.
pacs.002 = status answer; camt.056 = cancellation/recall request → apply: enquiry port of the batch rail adapter.
Recon is the resolution backstop that always terminates UNKNOWN → apply: wire W6's matcher to close parked sagas.
Customer during UNKNOWN sees pending + held funds, not an error → apply: status API mapping.
