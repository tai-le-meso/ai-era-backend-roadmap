What I learn
Modelling rails as strategiesEach adapter implements the same port but returns different semantics: InstantRail → final on ack; BatchRail → accepted-into-batch, settlement at cycle time, returns window open for days; RtgsRail → final on processing, no returns. Failure semantics differ too: instant rails reject synchronously; batch rails accept then bounce asynchronously — the port contract must allow both.
Parsing pacs.008 for realGenerate/write JAXB (or streaming) bindings from the XSD, parse a sample message, and map into your domain Payment with Money (5A-W4) and references intact. Validate against the XSD and reject on failure — schema validation is your first compliance control on inbound data.
What I do
  1. Implement the PaymentRail port and three adapters with distinct timing/finality/failure behaviour (simulated clearing cycles for the batch rail).
  2. Implement and test the pacs.008 parser against a sample message; assert field-level mapping including EndToEndId and settlement amount.
  3. Wire each adapter's settlement/return events into the 5A ledger via the posting service (auth-hold, settle, return-reversal).
  4. Test the batch adapter's late-return path end-to-end: settle, then return after 'two days' (simulated clock).
What I conclude
  • Different finality semantics = different ledger choreography per rail; the strategy pattern keeps that difference explicit and testable.
  • Schema-validated parsing at the boundary keeps malformed partner data out of the domain — reject early, log the message id.
What I remember & apply
Batch adapter: accept ≠ settle ≠ immune-to-return; three distinct ledger moments → apply: state machine wiring in 5B-W2.
Validate inbound ISO 20022 against XSD before mapping → apply: partner integration hardening in 5B-W6.
Simulated clock for cycle/cut-off tests → apply: cut-off chaos tests in 5B-W6.
