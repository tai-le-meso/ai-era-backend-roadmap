What I learn
Financial integration auth is transport-heavyPartner integrations use mutual TLS with client certificates (which EXPIRE — cert expiry is a top-3 cause of partner outages; monitor validity as a metric), IP allowlisting (breaks silently when egress IPs change — pin them), and signed messages on top. Sandbox and production drift: different certs, different endpoints, and sandbox behaviour that is more forgiving than production — test-passed-in-sandbox is weak evidence.
Webhook delivery and verificationFrom Stripe's model: sender signs payload with HMAC-SHA256 including a timestamp; receiver verifies signature (constant-time compare), rejects stale timestamps (replay window ~5 min), handles DUPLICATES (dedupe on event id), tolerates out-of-order delivery, and returns 2xx immediately with async processing (slow handlers cause timeout-retry storms). Sender retries with backoff for days — your handler will see the same event again; idempotency is mandatory, which you already built in W2.
SFTP batch integration failure modesThe classic channel, with classic failures: partial files (read a file mid-upload — use upload-then-rename or done-markers), duplicate files (resent after 'no ack'), missing files (silence is a failure mode — alert on ABSENCE at deadline), corrupt transfer (verify checksums), and reordered processing. Nacha-style file structure shows the defence: control totals and entry counts inside the file let you verify integrity independently of transport.
What I do
  1. Read Stripe's webhook signature and best-practices sections; write your inbound-webhook checklist (verify, timestamp-check, dedupe, 2xx-fast, async).
  2. Read the EPC SCT processing-timeline material; write down the cut-off concept and what happens to a payment that misses a cycle.
  3. List every flagship↔partner touchpoint and its channel (API, webhook, file); annotate each with its auth mechanism and top failure mode.
  4. Design the SFTP flow: done-marker or rename protocol, checksum verification, duplicate-file ledger (reuse 5A-W6's checksum dedupe), missing-file deadline alert.
What I conclude
  • Partner integration failure modes are boring and enumerable — certs, IPs, duplicates, partials, silence — which means checklists beat cleverness.
  • Absence of an expected file is an incident that no exception handler will throw — you must alert on what DIDN'T happen.
  • Everything inbound is untrusted until signature-verified and deduplicated, even from a contracted partner.
What I remember & apply
Webhook receiver: verify HMAC (constant-time), enforce replay window, dedupe by event id, 2xx fast → apply: day-3 signed-webhook build.
Cert expiry and IP changes are silent partner-killers; monitor both → apply: ops checks in v5.5.
SFTP: rename-on-complete + checksum + duplicate-file detection + absence alerts → apply: day-3 batch flow.
Sandbox ≠ production (certs, endpoints, leniency) → apply: connectivity smoke tests per environment.
