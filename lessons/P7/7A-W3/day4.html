What I learn
What should not be a toolAnything destructive without confirmation, anything that could exfiltrate bulk data, and anything whose authorisation cannot be checked per call. Deciding this before W4's write tools is the safe order.
Descriptions as the leverEstablishing this now — that model behaviour is steered by descriptions — sets up the tool-security work next week, where the description must also constrain misuse.
What I do
  1. Finish the read-only MCP server.
  2. Write the Reason answers.
  3. Run the AI drill and fix selections through descriptions.
  4. Commit the server and a real session transcript.
What I conclude
  • Reason (write it out): which flagship capabilities should be MCP tools and which absolutely should not? What makes a good tool description — remember it is a prompt, not documentation.
  • AI drill: give the model your tool schemas and a task, and watch which tools it picks. Where it picks wrong, the fix is almost always the description.
  • The description-not-code insight is the single most useful practical lesson about MCP.
What I remember & apply

Deliverable: read-only MCP server + real session transcript → apply: W4 adds write tools with authorisation.
