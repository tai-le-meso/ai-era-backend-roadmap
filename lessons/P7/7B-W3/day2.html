What I learn
The refactor with a safety netPick a real refactor — migrating a module to a new abstraction. Run the tests before, apply the change, run them after. The suite is what makes the speed safe.
AI for debuggingGive it the stack trace, the relevant code and the logs, and ask for ranked hypotheses. It is good at generating candidates and poor at knowing which is right. Verifying each hypothesis rather than accepting the first plausible one is the discipline.
Bug classes AI missesOff-by-one in boundary conditions it cannot see tested, race conditions (no execution model), and isolation-level bugs (needs database semantics plus concurrency). These are the classes you must own — and they map exactly onto the hardest material in Phases 1–3.
What I do
  1. Perform one large AI-assisted refactor behind the test suite.
  2. Inject three subtle bugs: an off-by-one, a race, a wrong isolation level.
  3. Use AI to debug each and record which it finds.
  4. Keep a debugging log: hypotheses offered, which was right, how long it took.
What I conclude
  • The bug classes AI misses are precisely the ones Phases 1–3 trained you on — that is not a coincidence.
  • Ranked hypotheses are useful; the first plausible one accepted without verification is a trap.
What I remember & apply
Verify each debugging hypothesis, don't accept the first → apply: plausible and wrong is the dangerous case.
AI misses off-by-one, races and isolation bugs → apply: these three classes stay yours, permanently.
Refactor behind a test suite → apply: the suite is what converts speed into safety.
