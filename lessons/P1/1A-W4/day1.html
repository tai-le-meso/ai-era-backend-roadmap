Learn I — Generics, exceptions & API design

Modern Java Mastery · Phase 1 — Engineering Foundation · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Generics beyond the basicsBounded types (<T extends Comparable<T>>), generic methods with inference, and the limits of inference — the compiler infers from arguments and target type, and gives up on deeply nested generic returns. @SafeVarargs exists because generic varargs create an array of an erased type, which is heap pollution waiting to happen.
Checked vs unchecked as a design decisionChecked exceptions force the caller to decide; unchecked let it propagate. The modern consensus is unchecked for programming errors and for anything the caller cannot meaningfully recover from — which is most things in a web service. The real question is not which type, but where the exception is translated.
Exception translation across layersA SQLException escaping to a controller is a layering failure. Each layer should translate into its own vocabulary: infrastructure → domain exception → HTTP problem. Losing the cause while translating is the common mistake — always pass the cause.
The real cost of exceptionsStack trace capture dominates the cost, not the throw. fillInStackTrace walks the stack; in a hot path an exception used for control flow can be orders of magnitude slower than a return value. Overriding fillInStackTrace for a truly hot signalling exception is a legitimate, documented technique.
What I do
  1. Read RFC 9457 §3 — the standard fields (type, title, status, detail, instance) and extension members.
  2. Write down where in your work codebase a low-level exception currently escapes its layer.
  3. In jshell, measure throw-with-stack-trace vs throw-with-overridden-fillInStackTrace in a tight loop — see the difference for yourself.
  4. Sketch the exception hierarchy you will build tomorrow: one base, a small number of subtypes.
What I conclude
  • The choice of checked vs unchecked matters far less than having exactly one place that decides the HTTP response.
  • An exception hierarchy with 30 types is as bad as one with none — aim for a base plus a handful that map to distinct responses.
  • Exceptions are for exceptional flow; using them for expected outcomes is a measurable performance decision, not just a style one.
What I remember & apply
RFC 9457 replaced RFC 7807 as the problem-details standard → apply: cite 9457 in API design docs.
Stack-trace capture is the expensive part of an exception → apply: never use exceptions for expected control flow in a hot path.
Always pass the cause when translating → apply: throw new DomainException(msg, e) — dropping e destroys the trail.
@SafeVarargs marks that you don't write to the generic varargs array → apply: only add it when that is actually true.
