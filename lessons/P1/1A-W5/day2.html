What I learn
Collectors that earn their keepgroupingBy with a downstream collector composes: group then count, group then map then join. teeing runs two collectors and merges — the clean way to compute min and max in one pass. partitioningBy beats groupingBy on a boolean because it always returns both keys.
When parallel losesParallel streams use the common ForkJoinPool. They lose when the source splits badly (LinkedList, Iterator-based), when per-element work is trivial so overhead dominates, or when the pipeline is IO-bound — and they are dangerous in a server because they contend on a JVM-wide pool.
Designing the comparisonToday's build is deliberately two implementations of the same reporting logic. The design question is what you will measure: not just wall time but readability and the diff size for a plausible future change.
What I do
  1. Implement the transaction reporting/query layer with streams — grouping, aggregation, a teeing for min/max in one pass.
  2. Implement the same logic imperatively with explicit loops.
  3. Design the comparison: what will you measure, at what input size, and how will you judge readability?
  4. Predict which will be faster and by how much, in writing, before running anything.
What I conclude
  • Collector composition is where streams genuinely beat loops — a three-level grouping is unreadable as nested loops.
  • The common ForkJoinPool being JVM-wide makes parallel streams a poor default in a shared server process.
What I remember & apply
Parallel streams use the shared common ForkJoinPool → apply: never use them in request-handling code in a server.
teeing computes two collectors in one pass → apply: use it wherever you currently stream twice.
partitioningBy always returns both true and false keys → apply: prefer it over groupingBy on a predicate.
