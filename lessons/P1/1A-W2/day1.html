What I learn
ArrayList vs LinkedList in realityArrayList is a contiguous array — random access is O(1) and iteration is cache-friendly. LinkedList is O(1) insert given a node, but you almost never have the node, and every element is a separate heap object with two extra pointers. In practice ArrayList wins nearly always, including for queue-like use where ArrayDeque beats both.
HashMap internalsBuckets are an array of size 2^n. A key's hashCode is spread (XOR with high bits) then masked. Collisions form a linked list, and at 8 entries in one bin with table size ≥64 the bin becomes a red-black tree; it untreeifies at 6. Resize doubles capacity at size > capacity * loadFactor (0.75) and rehashes everything.
Iteration-order guaranteesHashMap guarantees nothing and its order can change on resize. LinkedHashMap guarantees insertion order — or access order if constructed with accessOrder=true, which is how you build an LRU. TreeMap guarantees comparator order.
Views vs copiesCollections.unmodifiableList(x) is a view — mutating x mutates what the caller sees. List.of(...) and List.copyOf(x) are genuinely immutable copies. Confusing the two is a real defect, not a style point.
Fail-fast iterationmodCount is bumped on structural modification; iterators check it and throw ConcurrentModificationException. It is a best-effort bug detector, not a thread-safety mechanism.
What I do
  1. Read the HashMap class javadoc end to end — it is one of the best-written docs in the JDK.
  2. In jshell, build a HashMap with deliberately colliding keys (same hashCode, different equals) and observe lookup degradation.
  3. Prove the view-vs-copy difference: wrap a list with unmodifiableList, mutate the original, print the wrapper.
  4. Write your own one-paragraph explanation of resize before reading anyone else's.
What I conclude
  • Choosing a collection is choosing an access pattern; the complexity table matters less than cache behaviour at realistic sizes.
  • unmodifiable* communicates intent to the caller but protects nothing if the source escapes.
  • Treeification is a defence against hash-collision DoS as much as a performance feature.
What I remember & apply
HashMap treeifies a bin at 8 entries when the table is ≥64, untreeifies at 6 → apply: a hot map with a poor hashCode degrades to O(log n), not O(1) — check the hash before blaming the map.
Default load factor is 0.75 → apply: pre-size maps you build in a loop with new HashMap<>(expected/0.75f + 1) to avoid repeated rehash.
List.of is an immutable copy; unmodifiableList is a view → apply: return List.copyOf from getters that expose internal state.
ArrayDeque beats Stack and LinkedList for both stack and queue use → apply: replace any Stack you find in the codebase.
