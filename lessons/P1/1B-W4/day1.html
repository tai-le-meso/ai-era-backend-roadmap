Learn I — Concurrency primitives & the Java Memory Model

JVM Internals, Concurrency & Performance · Phase 1 — Engineering Foundation · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
Executors and their queuesnewFixedThreadPool uses an unbounded LinkedBlockingQueue — under overload it grows until OOM rather than rejecting. newCachedThreadPool creates unbounded threads. Neither is safe as a default in a service; construct ThreadPoolExecutor explicitly with a bounded queue and a rejection policy.
CompletableFuture and the executor it actually runs onWithout an explicit executor, async stages run on the common ForkJoinPool — shared JVM-wide, sized to CPU count, and not meant for blocking work. Blocking on it starves everything else in the process.
Locks: synchronized vs the explicit onessynchronized is simple and biased/thin-lock optimised. ReentrantLock adds tryLock, timeouts, fairness and interruptibility. ReadWriteLock helps only when reads massively dominate and hold time is non-trivial; otherwise its bookkeeping costs more than it saves.
The Java Memory ModelWithout a happens-before edge, one thread's write need never become visible to another — the compiler and CPU may reorder freely. volatile writes happen-before subsequent volatile reads of the same field; lock release happens-before subsequent acquire; final fields are frozen at constructor exit if this did not escape.
What I do
  1. Read the java.util.concurrent package javadoc section on memory-consistency effects.
  2. Write down the happens-before edge for each construct you currently use at work.
  3. In jshell, demonstrate a lost update with two threads and an unsynchronised counter.
  4. Check your work codebase for Executors.newFixedThreadPool and note the queue behaviour under overload.
What I conclude
  • The unbounded queue in the standard factory methods is a production hazard hiding behind a convenient API.
  • volatile gives visibility and ordering but not atomicity — volatile int i; i++ is still a race.
What I remember & apply
Executors.newFixedThreadPool has an unbounded queue → apply: build ThreadPoolExecutor explicitly with a bounded queue + CallerRunsPolicy or explicit rejection.
CompletableFuture async stages default to the common ForkJoinPool → apply: always pass an explicit executor for anything that blocks.
volatile = visibility + ordering, not atomicity → apply: use AtomicInteger for counters, never volatile int.
Final fields are safely published only if this didn't escape the constructor → apply: never start a thread or register a listener from a constructor.
