What I learn
Hot-row throughput mathsIf a hot-row update takes 5ms including commit, that row supports ~200 updates/sec no matter what. Adding application threads adds queueing, not throughput. This is the constraint that shapes ledger design in Phase 5.
Two fixesOrdered locking prevents deadlocks by ensuring all transactions acquire in the same order — cheap and always correct. Sharded counters (N rows per logical account, summed on read) trade read cost for write parallelism and are how high-throughput ledgers actually work.
SKIP LOCKED for queuesSELECT ... FOR UPDATE SKIP LOCKED LIMIT n gives each worker a disjoint batch with no coordination. The cost is no ordering guarantee across workers and the risk of starving a row that is always skipped.
What I do
  1. Build the hot-row scenario: all load to one account, measure throughput collapse.
  2. Fix it with ordered locking and measure.
  3. Fix it with a sharded counter and measure.
  4. Build a small SKIP LOCKED work queue and measure worker scaling.
What I conclude
  • Throughput on a hot row is bounded by transaction latency; the only fixes are shortening the transaction or removing the single row.
  • Sharded counters are the standard answer and they complicate reads — write down that trade-off now, you will reuse it in 5A.
What I remember & apply
Hot-row ceiling ≈ 1 / transaction latency → apply: compute it before promising a TPS number.
Consistent lock ordering prevents most deadlocks → apply: document the ordering rule in the repository layer.
SKIP LOCKED gives disjoint batches → apply: use it for the outbox relay; beware row starvation.
