What I learn
The single-threaded execution modelRedis executes commands one at a time on one thread. That is why every operation is atomic without locks — and why one slow command blocks everything. KEYS * on a large database is a production incident; SCAN iterates in bounded chunks and is the only safe way to walk the keyspace.
Data types and their real costStrings for simple values. Hashes for objects (and small hashes are memory-optimised as ziplists). Sorted sets for leaderboards, rate limiters and time-ordered queues — O(log n) inserts with range queries. HyperLogLog for approximate cardinality in ~12KB regardless of set size.
Persistence and what a crash costsRDB is a point-in-time fork-and-dump — compact, fast restart, and you lose everything since the last snapshot. AOF logs every write; with everysec fsync you lose up to a second. Neither makes Redis a system of record — this is the core of the week's key question.
Eviction policiesWith maxmemory set, allkeys-lru evicts any key, volatile-lru only keys with a TTL, volatile-ttl prefers the soonest-expiring. With noeviction writes fail once full. Choosing wrong means either surprise data loss or surprise write failures.
What I do
  1. Read the Redis data-types overview and note which flagship use cases map to which type.
  2. Set maxmemory low deliberately and observe eviction behaviour under each policy.
  3. Time KEYS * vs SCAN on a 1M-key database and see the blocking difference.
  4. Write down what your flagship would lose if Redis restarted right now.
What I conclude
  • Single-threaded execution gives free atomicity and makes one slow command everyone's problem.
  • Persistence modes bound your data loss; neither eliminates it. That constrains what Redis may hold.
What I remember & apply
KEYS blocks the whole server; use SCAN → apply: ban KEYS in code review, no exceptions.
AOF everysec loses up to 1s of writes; RDB loses since last snapshot → apply: never store un-recomputable data in Redis.
noeviction makes writes fail when full → apply: choose the policy deliberately; the default may not be what you want.
Sorted sets are O(log n) with range queries → apply: the right structure for rate limiters and time-ordered queues.
