Learn I — Fundamentals & the log

Kafka & Event-Driven Architecture · Phase 2 — Data & Messaging · ~4.5h
Day 1 — Learn IDay 2Day 3Day 4↑ Week overview
What I learn
The log as the primitiveA partition is an append-only, immutable, ordered sequence. Consumers track an offset; nothing is deleted on read. Retention is by time or size, or compaction keeps the latest value per key. This is the whole model — everything else is bookkeeping on top of it.
Partitions and orderingOrdering is guaranteed within a partition only. The partition is chosen by key hash (or round-robin if keyless). So 'ordered by account' means 'keyed by account id' — and that immediately creates the hot-partition problem when one account dominates traffic.
Producer durability knobsacks=0 fire and forget. acks=1 leader only — lose the leader before replication and the record is gone. acks=all waits for all in-sync replicas — combined with min.insync.replicas=2 it survives one broker loss. acks=all with min.insync.replicas=1 gives you almost nothing, because the leader alone can be the only ISR.
The consumer poll-loop contractpoll() both fetches records and signals liveness. Take longer than max.poll.interval.ms to process a batch and the broker assumes you are dead and rebalances the partition away — while you are still writing to it. This causes duplicate processing and is one of the classic Kafka production surprises.
What I do
  1. Stand up Kafka + Schema Registry in Docker Compose.
  2. Publish TransferInitiated from the flagship; consume it in a notification handler.
  3. Read the replication section and write down what min.insync.replicas actually guarantees.
  4. Predict what happens when you kill a broker mid-produce with acks=1.
What I conclude
  • Ordering is a per-partition property, so the key choice is the ordering design.
  • acks=all is only meaningful together with min.insync.replicas ≥ 2.
What I remember & apply
Ordering holds within a partition only → apply: pick the key by the ordering requirement, then check the skew.
acks=all + min.insync.replicas=1 gives no real durability → apply: set both explicitly, always.
Exceeding max.poll.interval.ms triggers a rebalance mid-processing → apply: keep batches small or increase the interval deliberately.
Compaction retains the latest value per key → apply: use for state topics, not for event history.
