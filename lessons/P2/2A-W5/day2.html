What I learn
Streaming replication and lagThe primary ships WAL to replicas. Async replication means the primary commits without waiting — fast, but a failover can lose the last transactions (non-zero RPO). Sync replication waits for a replica's confirmation — zero data loss, but primary latency now includes network round-trip and a replica outage can stall writes.
Read-after-write on replicasRoute a read to a replica immediately after a write and the row may not be there yet. This is the single most common bug introduced by adding read replicas, and it is a correctness bug that appears intermittently under load.
Connection pooling mathsA PostgreSQL connection is a process with real memory cost; a few hundred is a lot. HikariCP should be sized from Little's Law and the database's capacity, not set to 100 by default. PgBouncer in transaction mode multiplexes many clients onto few server connections — but breaks session-scoped features: prepared statements, advisory locks, SET session state, and LISTEN/NOTIFY.
What I do
  1. Add a streaming replica in Docker Compose.
  2. Route reads to the replica and reproduce the read-after-write bug.
  3. Implement two fixes: sticky-to-primary for N seconds after a write, and a write-timestamp/LSN token.
  4. Size HikariCP from your measured latency and target throughput, not a default.
What I conclude
  • Read replicas trade consistency for capacity; the trade must be made per read path, not globally.
  • PgBouncer transaction mode is excellent and it silently breaks prepared statements — know before you deploy it.
What I remember & apply
Async replication = non-zero RPO on failover → apply: state your acceptable data-loss window explicitly.
Read-after-write breaks on replicas → apply: route reads that follow a write to the primary, or carry an LSN token.
PgBouncer transaction mode breaks prepared statements and session state → apply: disable server-side prepared statements in the JDBC driver if you use it.
Size the pool from Little's Law → apply: pool = throughput × latency, capped by what the DB can serve.
