Kafka & Event-Driven Architecture · Phase 2 — Data & Messaging · ~4.5h

What I learn
Schema Registry in the pipelineThe producer registers the schema and writes a schema id in the record header; the consumer fetches the schema by id and resolves. Compatibility is enforced at registration time — which is why wiring the check into CI catches breakage before deploy rather than at runtime.
Event design choicesA thin event (TransferInitiated{transferId}) forces consumers to call back for details — low coupling on data, high coupling on availability. Event-carried state transfer (full transfer details in the event) lets consumers work independently at the cost of a larger contract and duplicated data.
Kafka Streams basicsA KStream is a record stream; a KTable is a changelog interpreted as current state per key — the stream-table duality. State stores are local, backed by a changelog topic for fault tolerance. Windowing (tumbling, hopping, session) plus grace periods handle late data.
What I do
  1. Migrate all flagship events to Avro with Schema Registry.
  2. Add a CI step that fails the build on an incompatible schema change.
  3. Perform a real evolution: add a field with a default; prove old consumers still work.
  4. Decide thin vs state-transfer for each event and record the reasoning.
What I conclude
  • A CI compatibility gate turns schema discipline from a review habit into a guarantee.
  • The thin-vs-fat event decision is really a coupling decision — make it deliberately per event.
What I remember & apply
Schema id travels in the record; the registry resolves it → apply: registry availability is now on your critical path — plan for it.
Enforce compatibility in CI → apply: catch the break at build time, not at 3am.
Thin events couple on availability, fat events couple on schema → apply: choose per event, document the choice.
