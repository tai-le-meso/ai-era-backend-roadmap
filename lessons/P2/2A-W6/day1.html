What I learn
Finding the real slow queriespg_stat_statements aggregates by normalised query text with total and mean time and call counts. Sort by total time, not mean — a 5ms query called 2 million times costs more than a 3-second report run once. auto_explain logs plans for anything over a threshold.
Spring transaction boundaries@Transactional propagation (REQUIRED vs REQUIRES_NEW), readOnly=true (which lets the driver and PostgreSQL optimise and prevents accidental writes), timeout, and rollback rules — by default Spring rolls back on unchecked exceptions only, so a checked exception silently commits.
The N+1 problemA query for N parents followed by N queries for children. In JPA it comes from lazy associations accessed in a loop. Fixes: JOIN FETCH, entity graphs, or batch fetching. It is the single most common performance bug in Spring Data applications.
Connection exhaustionWhen the pool is empty, callers block for connectionTimeout then fail. From the user's side this looks like a total outage even though the database is healthy — the symptom and the cause are far apart, which is why this is worth rehearsing.
What I do
  1. Enable pg_stat_statements and auto_explain on the flagship.
  2. Sort by total time and identify the true top-5 cost centres — they will differ from your assumptions.
  3. Find and fix at least one N+1 with JOIN FETCH or an entity graph.
  4. Deliberately exhaust the connection pool under load and observe what the client sees.
What I conclude
  • Total time, not mean time, identifies what to optimise.
  • Default Spring rollback rules surprise people: a checked exception commits unless you configure otherwise.
What I remember & apply
Sort pg_stat_statements by total time → apply: the frequent cheap query usually beats the rare expensive one.
Spring rolls back on unchecked exceptions only by default → apply: set rollbackFor explicitly when you use checked exceptions.
readOnly=true enables real optimisations → apply: annotate every read-only service method.
N+1 is the default failure mode of lazy JPA associations → apply: enable SQL logging in tests and count queries.
