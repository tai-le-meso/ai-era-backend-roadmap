What I learn
Expand–contract migrationNever change a column in place under load. Expand: add the new column, backfill in batches, dual-write. Migrate: switch reads to the new column. Contract: stop writing the old one, then drop it. Each step is independently deployable and reversible.
Which ALTERs are safeAdding a nullable column is fast (metadata only). Adding NOT NULL with a default is fast in modern PostgreSQL. Adding an index takes a lock unless you use CREATE INDEX CONCURRENTLY. Changing a column type usually rewrites the whole table under ACCESS EXCLUSIVE — the outage case.
Backfilling safelyBatch the backfill in chunks with a commit between each, or you hold a transaction open across millions of rows — blocking vacuum and bloating the table (the Week 5 lesson, in production form).
What I do
  1. Write the flagship's migrations as Flyway versioned scripts.
  2. Perform a real expand–contract column rename while k6 load is running.
  3. Use CREATE INDEX CONCURRENTLY and confirm no blocking.
  4. Batch a backfill and verify it does not hold a long transaction.
What I conclude
  • Zero-downtime migration is a sequence of safe steps, not a clever single statement.
  • CREATE INDEX CONCURRENTLY is slower and does not block — always the right trade in production.
What I remember & apply
Expand → backfill in batches → switch reads → contract → apply: memorise this sequence; it is the answer to every schema-change question.
CREATE INDEX CONCURRENTLY avoids the write lock → apply: never plain CREATE INDEX on a live table.
Type changes rewrite the table under ACCESS EXCLUSIVE → apply: add a new column instead, then expand-contract.
